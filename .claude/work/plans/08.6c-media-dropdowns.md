# 08.6c: Dropdowns in the Media dialog

> Historical: built and committed; see the roadmap for what followed.

**Goal:** the Media dialog's type filter and sort, and the Tags dialog's
sort, become dropdowns; Grid / List stays as it is.
**Specs:** the user's request (2026-10-07), with the choice made the same
day: type and sort as dropdowns, view unchanged; then the Tags dialog's
sort as well ("please change to dropdown").
`.claude/work/specs/documents.md` decision 11 (the Media dialog);
`.ai/rules/design-system.md` (Ark wrapped, never used directly).
**File format impact:** none.
**UI impact:** one component added, `Select`: Ark UI's `Select` wrapped, a
labelled trigger showing the chosen option and a list to pick from. Used by
`MediaDialog` for Type and Sort, and `TagsDialog` for Sort. Strings in `messages.ts`; tokens added
first if needed.

## Constraints

- Ark's `Select` through the new wrapper only; its Svelte API looked up
  (Context7 `/chakra-ui/ark`), never ported from React.
- Same behaviour as today: the same filters (All, Images, Videos, PDFs,
  Other, Unused) and sorts (Name, Size, Date), the same defaults, and what
  is chosen still narrows and orders the files at once.
- Keyboard: the trigger opens with Enter, Space or the arrows; arrows move;
  Enter picks; Escape closes and gives focus back to the trigger.
- Each dropdown is named for a screen reader ("Type", "Sort by"), and shows
  its choice: "All types", "Sort: Name".

## As built

The Media dialog's Type and Sort, and the Tags dialog's Sort, are
dropdowns over a new `Select` (Ark's Select wrapped): a trigger showing the
choice ("All types", "Sort: Name") and a list with a check by it. Grid /
List is unchanged. Type's first option now reads "All types" and the
filter is named "Type".

**Checks:** `npm test` 2,763 passed and 1 skipped; `npm run browser` 468
passed (one run of two clean; the other met a rare flake, below), no unused
references; the Media and Tags
dialog pictures and the controls sheet retaken, and a picture of the open
Type list added, read in both themes.

**Deviations, and two bugs found on the way**

- **The dropdown's list mounts only while open.** A modal dialog marks
  everything outside it hidden from screen readers when it opens; a list
  mounted before then stayed hidden inside the dialog.
- **Menus take the keys when they open** (`ContextMenu`): Ark left focus
  on the button or place that opened them, so arrow keys never reached a
  menu opened from a button.
- **A dialog's own menus are drawn inside it** (`ContextMenu within`, the
  Tags and Templates dialogs): drawn in the portal, the dialog's focus trap
  pulled the keys back from them, and a menu losing focus closed, sometimes
  before a click on an item counted. This was the flaky Tags merge test,
  traced by logging the menu's events (a close with no choice), then the
  focus moving back and forth.
- The integration tests wait for a menu to hold the keys before choosing
  from it, as a person sees it ready.

**Review:** no blockers. Fixed: a menu opened from a button gives the
keys back to it when it closes with nowhere else to go (Ark has no trigger
of its own to give back to), with a test; the dropdown is named by a
visually hidden label, so its list and hidden select are named too, with a
test that the label names the trigger; Escape on a dropdown gives the keys
back to it (tested); a `check` icon id for the dropdown's check; the jsdom
`scrollTo` stand-in shared in the test setup; a picture of a menu open
inside the Tags dialog, drawn past its edge. Left: `ContextMenu`'s focus
and `within` are covered by the browser tests, as Ark's menu does not open
under jsdom.

**A rare flake seen once, not from this change:** "saving after a change of
theme draws the picture again" (8.5) found the page still unsaved after
five seconds in one full run under load; it passes ten of ten alone.

**Left to a person at a running window:** the dropdowns and menus inside
the Media, Tags and Templates dialogs by keyboard on each platform's
webview.
